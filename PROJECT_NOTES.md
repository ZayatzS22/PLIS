# 1. Главная цель проекта

Наше предприятие производит **линейные направляющие**.

У Bosch существуют собственные линейные направляющие и разработанные под них высокоточные измерительные датчики / системы IMS.

Наша конечная цель — разработать **собственную систему датчиков для линейных направляющих нашего производства**.

То есть Bosch IMS для нас является прежде всего:

- техническим ориентиром;
- примером того, какие возможности можно получить;
- источником идей по принципам измерения и обработке сигналов;
- промышленным примером уже законченной высокоточной системы.

Задача не состоит в буквальном копировании Bosch IMS. Необходимо разработать решение, подходящее именно для наших направляющих, нашей механики, наших датчиков и нашей электроники.

# 2. Наша задача как программистов

Главная программная задача проекта — **придумать, проверить и реализовать алгоритм работы будущего датчика**.

То есть необходимо пройти путь примерно от сырых электрических сигналов датчика до полезного измерительного результата.

Упрощённо:

```text
физическое перемещение каретки
        ↓
чувствительный элемент / датчики
        ↓
аналоговые сигналы
        ↓
АЦП
        ↓
цифровые отсчёты
        ↓
FPGA / алгоритм обработки
        ↓
определение положения / перемещения
        ↓
выходные данные системы
```

На текущем этапе мы ещё не считаем алгоритм окончательно определённым. Стенд нужен именно для того, чтобы экспериментально понять сигналы и построить устойчивый алгоритм.

В программной части потенциально потребуется решать такие задачи, как:

- получение двух каналов измерительных данных;
- синхронная обработка каналов;
- фильтрация шумов;
- нормализация амплитуды и смещения;
- определение положения по форме сигналов;
- вычисление направления движения;
- обработка переходов между периодами сигнала;
- повышение разрешения за счёт интерполяции;
- компенсация погрешностей реального датчика и механики;
- калибровка;
- контроль неправильных / недостоверных состояний;
- передача итогового результата внешней системе.

Какие именно методы будут использоваться, нужно определять по реальным сигналам стенда и по дальнейшему изучению IMS.

# 3. Зачем сейчас используется Xilinx SP605

**Xilinx SP605 / Spartan-6 — это текущая экспериментальная платформа разработки.**

Она не обязательно является конечной аппаратной платформой будущего промышленного датчика.

Сейчас SP605 позволяет:

- подключить реальный измерительный стенд;
- получать данные с АЦП;
- генерировать необходимые управляющие сигналы;
- обрабатывать данные в FPGA;
- передавать данные на ПК;
- выдавать сигналы обратно через ЦАП;
- быстро менять Verilog-код и проверять различные алгоритмические идеи.

То есть текущий стенд нужен прежде всего для **исследования и разработки алгоритма будущего датчика**.

# 5. АЦП основного стенда — AD7357

На основном стенде используется **Analog Devices AD7357**.

Основные свойства:

- два канала;
- одновременная выборка обоих каналов;
- SAR АЦП;
- 14 полезных бит;
- полный цифровой диапазон 0...16383;
- отдельные последовательные линии `SDATAA` и `SDATAB`;
- интерфейс с `CS` и `SCLK`.

## Формат слова AD7357

При чтении 16 тактов выдаётся:

```text
00 D13 D12 D11 ... D2 D1 D0
```

То есть:

```text
[15:14] = два ведущих нуля
[13:0]  = 14-битный результат измерения
```

После приёма в FPGA:

```text
adc_out_x[15:14] = 00
adc_out_x[13:0]  = код 0...16383
```

# 6. `adc_receiver.v`

Файл:

```text
Main/sin_gen/adc_receiver.v
```

Назначение — принять два последовательных потока от AD7357.

Модуль получает:

```verilog
input data_a,
input data_b
```

и формирует:

```verilog
output reg [15:0] data_out_a,
output reg [15:0] data_out_b,
output reg        data_ready
```

Внутри используются 16-битные сдвиговые регистры:

```verilog
reg [15:0] shift_a;
reg [15:0] shift_b;
```

Каждый принятый бит сдвигается внутрь регистров. После получения полного слова значения передаются в `data_out_a` / `data_out_b`, а `data_ready` показывает, что новая пара отсчётов готова.

Важно: модуль сохраняет полный 16-битный формат интерфейса АЦП. Он сам не преобразует его в отдельный 14-битный тип.

---

# 7. UART основного проекта

В `Main/sin_gen/sin_gen.v` данные АЦП также передаются на ПК через `uart_transmitter` из `uart_tx.v`.

Параметры:

```text
CLK       = 27 МГц
BAUD      = 115200
DATA_BITS = 8
формат    = 8N1
```

На один результат двух каналов отправляются четыре байта:

```text
A_LOW
A_HIGH
B_LOW
B_HIGH
```

То есть по UART передаются полные 16-битные слова обоих каналов.

## Синхронизация

В основном проекте используется маркер:

```text
A5
```

Формат потока:

```text
A5
128 кадров данных
A5
128 кадров данных
...
```

Один кадр:

```text
A_LOW A_HIGH B_LOW B_HIGH
```

Для основного стенда однобайтовый `A5` пока оставляем — по информации коллеги этого достаточно.

# 8. ЦАП MAX5853

ЦАП управляется отдельным модулем:

```text
Main/sin_gen/max5853_dual_cntrl.v
```

Его интерфейс рассчитан на два 10-битных значения:

```verilog
input wire [9:0] data_a,
input wire [9:0] data_b,
output reg [9:0] dac_data
```

Модуль:

- выполняет начальную управляющую последовательность;
- формирует такт ЦАП;
- поочерёдно выдаёт канал A и канал B на общую 10-битную шину данных.

Поэтому этот файл является интерфейсом между основной логикой FPGA и физическим MAX5853.

---

# 9. Изначальная работа ЦАП

В старом основном проекте FPGA сама генерировала синус и косинус:

```verilog
wire [9:0] sin_out;
wire [9:0] cos_out;
```

через `sine_lut` и `cose_lut`.

Именно эти значения передавались на ЦАП:

```verilog
.data_a(sin_out),
.data_b(cos_out),
```

Таким образом, ЦАП раньше использовался для выдачи искусственно сформированных сигналов, а не текущих измерений АЦП.

# 10. Текущая доработка MAIN — передача АЦП на ЦАП

Новая задача основного стенда:

> Значения, которые реально измеряет AD7357, нужно продолжать передавать на ПК и одновременно выдавать через ЦАП.

UART при этом не изменяется.

AD7357 имеет 14 полезных бит:

```text
0...16383
```

а существующий контроллер MAX5853 принимает 10 бит:

```text
0...1023
```

Поэтому для ЦАП используются 10 старших полезных бит результата:

```verilog
adc_out_a[13:4]
adc_out_b[13:4]
```

В `sin_gen.v` изменено только подключение входов ЦАП.

Было:

```verilog
.data_a(sin_out),
.data_b(cos_out),
```

Стало:

```verilog
.data_a(adc_out_a[13:4]),
.data_b(adc_out_b[13:4]),
```

В результате:

```text
AD7357 A ──> FPGA ──┬──> UART -> ПК
                     └──> MAX5853 A

AD7357 B ──> FPGA ──┬──> UART -> ПК
                     └──> MAX5853 B
```

Остальную рабочую логику специально не меняли.

Не изменялись:

- `adc_receiver.v`;
- UART;
- `A5`;
- блоки по 128 кадров;
- UCF / назначение пинов;
- логика `max5853_dual_cntrl.v`;
- существующее тактирование.

Следующий этап — проверить эту версию непосредственно на основном стенде.

# 11. Офисный тестовый проект

В `Test/` находится отдельный проект без физического АЦП.

Для проверки полного 14-битного диапазона FPGA генерирует:

```text
канал A: 0 -> 1 -> ... -> 16383
канал B: 16383 -> 16382 -> ... -> 0
```

Поэтому для каждого кадра:

```text
A + B = 16383
```

Это позволяет хорошо обнаруживать:

- перестановку каналов;
- ошибки порядка байтов;
- потерю байта;
- сдвиг границы кадра.

В тестовой версии использовался синхромаркер:

```text
FF FF
```

вместо одного `A5`.

Причина: при прогоне всех значений число 165 равно `0x00A5`, поэтому байт `A5` естественно встречается внутри данных и может быть ошибочно принят программой за начало блока.

Эта логика относится к тестовому проекту и не означает, что `FF FF` обязательно нужен на MAIN.

# 14. Главный вопрос дальнейшей разработки

Аппаратный обмен FPGA с АЦП, UART и ЦАП — это инфраструктура стенда.

Главная исследовательская задача находится выше этого уровня:

> **Как по сигналам будущего датчика надёжно и с высокой точностью определить положение каретки линейной направляющей?**

Именно вокруг этого должен постепенно формироваться основной алгоритм.

Нужно исследовать реальные формы сигналов на стенде и понять:

1. Какие сигналы формирует чувствительная часть датчика при движении.
2. Как связаны два измерительных канала.
3. Насколько они близки к синусному и косинусному сигналам.
4. Как меняются амплитуда, постоянная составляющая и фазовый сдвиг.
5. Какие искажения даёт реальная механика направляющей.
6. Как влияет скорость движения.
7. Как влияет направление движения.
8. Какие шумы и помехи присутствуют.
9. Как восстановить положение внутри одного периода сигнала.
10. Как правильно считать переходы между периодами, чтобы получать абсолютное/накопленное перемещение.
11. Какая калибровка потребуется для каждой конкретной направляющей или датчика.
12. Какую часть алгоритма целесообразно выполнять непосредственно в FPGA, а какую — на внешнем контроллере/ПК во время исследований.

До получения и анализа реальных сигналов нельзя заранее считать какой-либо конкретный алгоритм окончательным.

# 15. Возможное направление алгоритма — пока только гипотеза

Если два физических канала датчика действительно будут близки к синусному и косинусному сигналам, потенциально может использоваться схема вида:

```text
A ≈ sin(φ)
B ≈ cos(φ)
```

Тогда положение внутри одного периода можно оценивать через фазу:

```text
φ = atan2(A, B)
```

а затем отслеживать полные обороты/периоды фазы и преобразовывать их в линейное перемещение.

Но это пока **не утверждённый алгоритм**, а направление для исследования.

На реальном датчике прежде могут потребоваться:

- удаление DC-offset;
- выравнивание амплитуд каналов;
- компенсация фазовой ошибки между каналами;
- коррекция эллипса вместо идеальной окружности в координатах A/B;
- фильтрация;
- таблица коррекции нелинейности;
- температурная компенсация;
- обработка ошибок и пропусков.

Материалы Bosch и реальные осциллограммы стенда должны помочь понять, какой алгоритм действительно нужен.
